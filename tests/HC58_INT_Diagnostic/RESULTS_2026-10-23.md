# HC58 INT Validation Results — 2026-10-23

## Scope

Hardware under test:

- Teensy 4.1
- Fixed Until Broken J1850 module, believed Rev C
- existing Big Dirty interface board
- HC58 INT routed to Teensy pin 0 through the existing level-shifting interface
- live vehicle J1850 VPW bus

Test traffic:

- functional Mode 01 request for PID `0x0B` (MAP)
- expected reply header `48 6B 10 41 0B`

The diagnostic deliberately did not initialize the display, touch controller, SD card, sensors, warning inputs, dimmer, page manager, or normal cluster application.

## Exact configuration A/B

```text
0x12 = 0001 0010   IMSK=1, interrupts disabled
0x02 = 0000 0010   IMSK=0, default interrupts enabled
```

IMOD remained zero. No other configuration field changed.

|---|---:|---:|---:|---:|---:|
| MASKED_POLL | 20 | 20 | 0 | 0 | 0 |
| IRQ_POLL | 20 | 20 | 43 | 0 | 0 |

The diagnostic printed:

```text
VERDICT MASKED_RECEIVE=PASS
VERDICT MASKED_ZERO_IRQ=PASS
VERDICT IRQ_POLL_RECEIVE=PASS
VERDICT IRQ_CORRELATION=PASS
```

The IRQ-only mode did not poll RxFIFO while waiting. It serviced the HC58 only after an ISR-recorded falling edge. Therefore this run proved that INT could drive successful reception rather than merely occurring alongside a polling receiver.

## 100-request IRQ-only run

Summary reported by the firmware:

```text
REQUESTS=100
VALID=100
TIMEOUTS=0
IRQ_EDGES=227
REQUESTS_WITH_IRQ=100
REQUESTS_WITH_MULTIPLE_IRQS=100
IRQ_LOG_OVERFLOWS=0
CLEANUP_REQUIRED=0
STALE_ITEMS=1987
FRAME_LIST_OVERFLOWS=0
```

Additional parsing of the preserved raw log produced:

- 73 requests contained exactly two completed frames: our request echo, then the PCM reply
- 27 requests contained three completed frames because unrelated vehicle traffic was also received
- 23 of those 27 were ordered `OUR_REQUEST -> BUS_FRAME -> PCM_MAP_REPLY`
- 4 were ordered `BUS_FRAME -> OUR_REQUEST -> PCM_MAP_REPLY`
- INT was high before and after every measured request
- every transmitted request completion code reported `TMS=TX_OK`
- every PCM reply reported `ERRF=0` and `RFO=0`
- the PCM-reply interrupt occurred from 12,771 to 36,872 microseconds after request loading in this run

## Verified conclusions

1. The physical INT path from the HC58 module through the interface board to Teensy pin 0 works.
2. Configuration byte `0x02` enables the default interrupt sources; `0x12` masks them.
3. Default IMOD=0 frame-completion interrupts are sufficient to receive the tested normal J1850 frames.
4. INT-driven RxFIFO service successfully received 100 consecutive PCM MAP replies without timed polling or fallback cleanup.
5. The HC58 generates an interrupt/completion for the frame transmitted by Big Dirty because it receives its own transmission.
6. Unrelated vehicle frames can appear before, between, or after the request echo and expected PCM reply.
7. Production software must identify frames by content and completion information, not by assuming a fixed interrupt count or order.
8. The HC58 continues collecting background traffic while the application is not actively waiting for a reply. Production firmware must therefore service the transport continuously, not only inside PID or DTC request functions.

## Interpretation of `STALE_ITEMS`

The diagnostic intentionally waited roughly one second between controlled requests and discarded accumulated RxFIFO traffic before the next request. The live vehicle bus continued producing frames during those gaps. `STALE_ITEMS=1987` documents that background traffic; it is not a request failure.

The production design consequence is important: background frames must still be drained, completed, counted, and discarded when no protocol consumer wants them.
